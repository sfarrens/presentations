## Linting

--

> Now, we have a pretty solid workflow for developing new features for our code and testing them. To keep things clean and consistent we can add another step to the workflow called *linting*.

> Linters are tools that automatically check (and often fix) code style and standards, against a given convention.

--

> Following the [Git workflow](#/5) we established previously, let's start by creating a feature branch for this work.

```bash
git checkout -b chore/add-linting
```

--

> [Ruff](https://docs.astral.sh/ruff/) is the current community standard for Python linting and formatting — a single, fast tool (written in Rust) that covers both.[$^{21}$](#/15/22)

--

> Since this is a development-only tool, we add it to a `lint` dependency group, the same way we did for `pytest`.

```bash
uv add --group lint ruff
```

--

> Just like `pytest`, we can configure `ruff` directly in `pyproject.toml`.

```toml
[tool.ruff]
line-length = 88
target-version = "py312"

[tool.ruff.lint]
select = ["E", "F", "I"]
```

> `E` and `F` cover style errors and common bugs (undefined names, unused imports, etc.), and `I` covers import sorting.[$^{22}$](#/15/23)

--

> We can now run `ruff` to reformat our code.

```bash
uv run ruff format .
```

> The formatter will inform us which files were modified.

--

> And we can run `ruff` again to check for lint issues and import order.

```bash
uv run ruff check .
```

> Some issues `ruff` can even fix for us automatically.

```bash
uv run ruff check --fix .
```

--

> There are many similar tools available for other standards and/or languages. The most important thing is to identify the tools that fit into your workflow for the standards you want to adhere to.

--

> So far we have had to remember to run `ruff` ourselves. It is easy to forget, and a good linting setup should catch issues *before* they even get committed. This is what [pre-commit](https://pre-commit.com/) is for — a framework that manages *git hooks*, small scripts that run automatically at key points in the Git workflow (e.g. just before a commit is created).

--

> Let's add `pre-commit` to our `lint` group too.

```bash
uv add --group lint pre-commit
```

> and create a configuration file for it.

```bash
touch .pre-commit-config.yaml
```

--

> A good starting point is to run `ruff` itself, along with a few other common, lightweight checks.

```yaml
repos:
  - repo: https://github.com/astral-sh/ruff-pre-commit
    rev: v0.16.2
    hooks:
      - id: ruff-check
        args: [--fix]
      - id: ruff-format
  - repo: https://github.com/pre-commit/pre-commit-hooks
    rev: v5.0.0
    hooks:
      - id: trailing-whitespace
      - id: end-of-file-fixer
      - id: check-yaml
      - id: check-added-large-files
```

--

> The second set of hooks are all fast, general-purpose checks (not Python-specific) that are common in most `pre-commit` setups: trimming trailing whitespace, ensuring files end with a newline, validating YAML syntax, and blocking accidentally-committed large files.[$^{23}$](#/15/24)

--

> Now we can install the hooks into our local repository.

```bash
uv run pre-commit install
```

> From now on, `ruff` (and the other hooks) will run automatically every time we run `git commit` — and the commit will be blocked if any issues are found. We can also run all hooks manually, against every file, at any time.

```bash
uv run pre-commit run --all-files
```

--

> Let's confirm this is actually working. Try adding an unused import to `cosmology.py`.

```python
import os
```

> Now try to commit as normal.

```bash
git add -A
git commit -m "Test pre-commit"
```

> The commit should be *blocked*, with `ruff` reporting the unused import before it ever reaches the repository. Remove the bad import, and you should be able to commit again.

--

> Make sure everything passes and then add, commit and push all of the changes to the feature branch.[$^{24}$](#/15/25)

```bash
git add -A
git commit -m "Add ruff linting and pre-commit hooks"
git push origin chore/add-linting
```

> Then open a Pull/Merge request as explained in the [previous section](#/5) before merging the changes.
