## Continuous integration and deployment II
### GitLab CI/CD

--

> Now that we have a good grasp on the premise of [continuous integration and deployment](#/10/1), we can take a look at how this works on GitLab.

--

> Following the [Git workflow](#/5) we established previously, let's start by creating a feature branch for this work.

```bash
git checkout -b chore/add-gitlab-ci
```

--

> For GitLab, we simply need to add a `.gitlab-ci.yml` file to the root directory of the repository.[$^{47}$](#/15/48)

```bash
touch .gitlab-ci.yml
```

--

> At the top of this file we will add the following.

```yml
image: ghcr.io/astral-sh/uv:python3.12-bookworm-slim
```

> Astral publish an official Docker image with `uv` and Python already installed, so there's no separate install step needed.[$^{48}$](#/15/49)

--

> Just like our GitHub cache, we can tell GitLab to cache `uv`'s package cache between pipeline runs.

```yml
variables:
  UV_CACHE_DIR: $CI_PROJECT_DIR/.uv-cache

cache:
  key: uv-cache
  paths:
    - .uv-cache/
```

--

> Now let's add a job for linting, which only needs to run when a merge request is opened.[$^{49}$](#/15/50)

```yml
lint:
  interruptible: true
  script:
    - uv sync --group lint
    - uv run ruff format --check .
    - uv run ruff check .
    - uv run mypy src
  rules:
    - if: '$CI_PIPELINE_SOURCE == "merge_request_event"'
```

--

> And a separate job to run our tests, under the same rule.[$^{50}$](#/15/51)

```yml
test:
  interruptible: true
  coverage: '/(?i)total.*? (100(?:\.0+)?\%|[1-9]?\d(?:\.\d+)?\%)$/'
  script:
    - uv sync --group test
    - uv run pytest
  rules:
    - if: '$CI_PIPELINE_SOURCE == "merge_request_event"'
```

--

> Let's add, commit and push all of the changes to the feature branch.

```bash
git add -A
git commit -m "Add GitLab CI workflow"
git push origin chore/add-gitlab-ci
```

> Then open a Merge Request as explained in the [previous section](#/5). Did your `lint` and `test` jobs both run?

--

> The final job will build and deploy our API documentation, whenever we push to `main`. `pages` is a reserved job name in GitLab — naming it this is what tells GitLab to publish the `artifacts` as a GitLab Pages site.[$^{51}$](#/15/52)

--

```yml
pages:
  script:
    - uv sync --group docs
    - uv run sphinx-apidoc -Mfeo docs/source src/mycosmo
    - uv run sphinx-build docs/source docs/build
    - mv docs/build public/
  artifacts:
    paths:
      - public
  rules:
    - if: '$CI_COMMIT_BRANCH == "main"'
```

--

> As with GitHub, it's worth enabling a merge check requiring `lint` and `test` to pass before a merge request can be merged, under Settings → Merge requests → Merge checks.

--

> Let's add, commit and push these changes to the same branch.

```bash
git add -A
git commit -m "Add pages job"
git push origin chore/add-gitlab-ci
```

> Then merge your Merge Request. Did your `pages` job run? Can you see your API documentation?
